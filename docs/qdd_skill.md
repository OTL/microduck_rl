## 技の仕様（schema_version 1。跳ぶ技は下の schema_version 2）

```json
{
  "schema_version": 1, "name": "bow", "description": "...",
  "duration_s": 3.0, "settle_s": 1.0, "interpolation": "minjerk", "support": "both_feet",
  "keyframes": [
    {"t": 0.0},
    {"t": 1.2, "joints_deg": {"hip_pitch": -55, "knee": 60, "ankle_pitch": -30}, "torso": {"pitch_deg": 25}},
    {"t": 1.9, "joints_deg": {"hip_pitch": -55, "knee": 60, "ankle_pitch": -30}},
    {"t": 3.0}
  ],
  "reward_weights": {"joint_tracking": 3.0}
}
```

- 関節角は絶対値（度）。書かない関節は立ち姿勢の値（hip_pitch -22.5、knee 45、ankle_pitch -22.5、ほか 0）。`hip_pitch` のように左右を付けない名前は両脚に左右対称で入る（yaw・roll は右で符号が逆）。
- 胴体の傾き・高さは関節角から計算する（両足の裏が床に平らに着いているとして順運動学）。`torso` は書き手の意図の確認用で、計算と 5 度・2 cm 以上ずれたら不合格。前傾（お辞儀）が pitch の正。
- 最初（t = 0）と最後（t = duration_s）のキーフレームは立ち姿勢でなければならない。そのあと `settle_s` の間、立ち姿勢に戻って止まることに報酬を出す。
- 報酬の重みは決まった範囲の中だけで変えられる（`qdd_skill.REWARD_WEIGHT_BOUNDS`）。バランス・両足の接地・最後の立ち姿勢は 0 にできない。
- 安全に関わるもの（終了条件、関節と膝の制限、ドメインランダム化、観測と行動の形式）は雛形で固定。仕様に `terminations` などを書くと不合格。

### 検証（LLM の出力が通る関門）

`python -m mjlab_microduck.tasks.qdd_skill <file.json | 名前>`（不合格なら終了コード 1、問題を全部、場所付きで出す）。調べること:

- 形（未知のキー、型、範囲、名前、時刻の順序と間隔 0.2 秒以上、最初と最後が立ち姿勢）
- 関節範囲（3 度の余裕）と姿勢で変わる膝の上限 `knee_max(hip_pitch)`（キーフレームと、その間の補間も）
- 参照の速さ: 関節 2.5 rad/s 以下、胴体の傾きの速さ 1.5 rad/s 以下
- 胴体: 前傾 -15〜30 度（コントローラは 35 度＋角速度、50 度で止める）、横傾き 10 度以内、高さ 0.24 m 以上
- 両足: 足裏が平行（3 度以内）で同じ高さ（1 cm 以内）、左右の間隔 0.08〜0.25 m
- 静的なバランス: 重心が両足の支持多角形の内側に 1.5 cm 以上

## 課題の中身

- 雛形は歩行課題そのもの（ロボット、アクチュエータ、ドメインランダム化、観測のノイズと遅れ、終了条件）。違いは下のとおり。
- **観測は歩行と同じ 41 次元**。指令の欄（36:39）は常に 0、歩容の位相の欄（39:41）に技の位相 `[sin(pi s), cos(pi s)]`（s = 経過時間 / (duration + settle)、0〜1）。
- エピソード = 技 1 回（duration + settle）。立ち姿勢から始める。学習では 30% のリセットを参照軌道の途中の姿勢から始める（reference state initialisation）。
- 報酬: 関節の追従、胴体の傾き・高さの追従、バランス（重心が流れない・回らない）、両足の接地、足の滑り、最後の立ち姿勢、行動の変化・トルク。固定: 関節・膝の制限、自己干渉、足裏を平らに、転倒の罰。
- 終了: 傾き 45 度（歩行は 60 度）、胴体 0.20 m 以下、足以外の接地、膝の制限、NaN。時間切れは技の終わり。
- 押し: ±0.15 m/s（歩行は ±0.3）。左右反転の損失は使わない（技は左右対称とは限らない）。
- 再生（play）: 歩行と同じ名目どおりのロボット、立ち姿勢から技を繰り返す。
- どの技を学習するか: 環境変数 `QDD_SKILL_SPEC`（パスか skills/ の名前）。無ければ `bow`。yatai は環境変数を渡せないので、yatai では既定の技（ブランチの bow.json）を学習する。

## 歩行の方策から始める（warm start）

yatai のハンドラは毎回まっさらに `train` を回し、チェックポイント（.pt）を返さないので、mjlab の `--agent.resume` は使えない。代わりに、技の runner（`QddSkillOnPolicyRunner`）が作られた直後に、**歩行の ONNX から actor の重みと観測の正規化**をそのまま読み込む（ONNX の中の名前が rsl_rl の `mlp.*` / `obs_normalizer` と同じなので、形が合えば写すだけ）。critic は新しく作る。行動のばらつきの初期値は 0.4（ゼロからなら 0.6）。

- 既定の初期値: `skills/warm_start/walk_gait2.onnx`。`QDD_SKILL_INIT_ONNX=<path>` で変更、`none` で無効。
- 歩行の方策は、指令 0 と技の位相を入れても立ったまま転ばない（確認済み）ので、バランスを保てるところから学習が始まる。

## 方策の入出力仕様（技）

技の ONNX には `policy_io`（技用）・`policy_io_sha256`・`skill_spec`（学習に使った JSON）を埋め込む。中身は歩行の policy_io.json と同じ（観測・行動・ゲイン）で、違いは:

- `"kind": "skill"` と `"skill"` 節（名前、duration_s、settle_s、total_s、n_steps、spec_sha256、開始と終了の条件）
- `gait_clock` を「技のクロック」として書いてある: `period_s = 2 * total_s`、`active_threshold = -1`（指令が 0 でも常に進む）、`initial_phase = 1 - dt / (2 * total_s)`（最初の観測で位相 0）。今の Rust コントローラはこの形をそのまま読めるので、`--mode walk --cmd 0,0,0` で技の方策を動かせる。
- `commands` の範囲は全部 [0, 0]。

技は total_s（= n_steps 回）で終わり、その後は学習していない（位相が 1 を越える）。止めるのはコントローラの役目。

## 跳ぶ技（schema_version 2、Mjlab-Skill-Hop-QddBiped）

両足ジャンプ（hop）のための拡張。version 1 の仕様はそのまま通る（接地はずっと両足、50 Hz）。根拠はロボットのリポジトリの `docs/jump-feasibility.md` と `analysis/hop.py`。

```json
{
  "schema_version": 2, "name": "hop", "interpolation": "pchip", "policy_rate_hz": 50,
  "contact": [{"t": 0.0, "feet": "both"}, {"t": 1.39, "feet": "none"}, {"t": 1.55, "feet": "both"}],
  "flight": {"com_rise_m": 0.03, "max_takeoff_speed_mps": 0.85, "max_landing_load_mg": 4.0, "toe_first": true},
  "keyframes": [...]
}
```

- `contact`: 接地の予定。t = 0 は両足、`both` と `none`（空中）が交互、最後は両足。空中は 1 回 0.06〜0.3 秒（コントローラは 0.3 秒で故障）、最大 3 回。離陸は 0.5 秒以降、最後の着地から終わりまで 0.5 秒以上。片足だけの区間は書けない。
- `flight`（空中があるときは必須）: 重心の上がる高さ（0.5〜4 cm）、離陸速度の上限（0.3〜0.9 m/s。重心 4 cm・0.9 m/s はモータバスの電流 LM5069 と着地のため）、片足あたりの着地荷重の上限（2〜4.5 mg。足首 GIM3510-8 のラジアル許容 300 N = 4.7 mg）、つま先から着地するか。空中の予定時間は弾道の 2 v0 / g と 0.06 秒以内で合っていること。
- `interpolation: "pchip"`: 単調な 3 次補間。押し出しの途中のキーフレームで速さが 0 にならない（minjerk は毎回止まる）。
- `policy_rate_hz`: 50 か 100。ONNX の policy_io の `policy_dt_s` に入る。
- 区間ごとの関門: 離陸の 0.15 秒前〜着地の 0.25 秒後（速い区間）は、関節の速さ 20 rad/s まで、キーフレームの間隔 0.02 秒まで、胴体の傾きの速さ 6 rad/s まで。離陸〜着地の 0.25 秒後（空中と着地の区間）は、足裏を床に平らに置いた計算（胴体の高さ・傾き、足裏の平行、静的なバランス）を調べない。胴体の前傾の上限は 40 度（しゃがみ 35 度のため）。キーフレームの `torso` はこの区間には書けない。
- 報酬の重みの追加: `flight_height`、`flight_rotation`、`landing_load`、`toe_first`、`takeoff_speed`、`joint_power`（空中があるときだけ使う）。`feet_contact` は接地の予定に従う報酬の重みになる。

### 課題（Mjlab-Skill-Hop-QddBiped、`skills/hop.json`）

yatai は環境変数を渡せないので、跳ぶ技は自分の課題 ID を持つ（`skills/hop.json` を学習する）。

- 物理 2.5 ms（足首の陽的 PD が 5 ms では不安定）、50 Hz なら decimation 8。
- アクチュエータ（`actuator/qdd_motor.py`）: ドライバの PD をそのまま陽に計算し、モータのトルク・速度の限界で切る（`analysis/hop.py` の `tmax()`。GIM6010-8 は FOC の電圧の限界・弱め界磁なし、22 V で 10 / 15 / 20 rad/s のとき 7.6 / 5.6 / 4.1 Nm。GIM3510-8 は 42.4 rad/s × V / 24 で 0 になる直線）。ブレーキ側（逆駆動）はドライバの範囲 11 / 6.28 Nm まで。
- 報酬（歩行の技の報酬に加えて）: 重心の高さの追従（押し出し〜空中、空中は目標の高さまでの弾道。高く跳んでも得をしない）、接地の予定（予定どおり両足が床 / 両足が空中。離陸・着地の前後 0.04 秒は左右そろっていれば満点、片足だけは 0）、離陸速度が上限を超えたら罰、空中の胴体の傾きの速さの罰、片足ごとの着地荷重（物理の 8 ステップの最大、上限の 0.6 倍から 2 乗、上限から 10 倍）、つま先から着地（着地の瞬間の足裏のつま先下がりの角度）、モータの出力（τ·ω の正の部分）。空中と着地の区間は、胴体の傾き・高さの参照と、足裏を平らにする罰を止める。速い区間は関節の追従を 2 倍ゆるく、行動の変化の罰を 0.1 倍にする。
- 参照の途中から始める（RSI）のは速い区間の外だけ。
- ドメインランダム化の追加: 足裏と床の接触の硬さ（solref の時定数 6〜30 ms、減衰比 0.7〜1.2：床とパッド）、モータバスの電圧 19.5〜24 V、モータの強さ ±10 %（トルクの上下限 GDK の 11 Nm はそのまま）。指令の遅れ 0〜10 ms は歩行と同じ。
- 2026-10-16 にロボットのリポジトリで足裏に 10 mm の TPU パッドが付いた（`ankle_to_sole` 0.040 → 0.050、6.623 kg）。`qdd_biped.xml` を作り直し、立ち姿勢の胴体の高さは 0.3542 m。歩行の方策（gait3 まで）はパッドなしで学習している。

### 2 回目（2026-10-17）：参照のフィードフォワード＋補正だけを学ぶ

1 回目は跳ばなかった。原因の一つは下位の制御そのもの：方策の出力は位置の目標だけで速度の目標は 0 なので、押し出しで関節が 15 rad/s で回ると、ドライバの D 項だけで Kd·ω = 1.2 × 15 = 18 Nm が動きと逆向きにかかる。そこで動き全体を下位が再生するフィードフォワードとして書き、方策はそれへの補正だけを学ぶようにした。

- 参照の表（`skills/hop_ref.json`、仕様の `"reference_table"`）：ロボットのリポジトリの `analysis/hop_reference.py` が `analysis/hop.py` から作る。5 ms ごとに関節の目標角 q・目標速度 dq・トルクのフィードフォワード tau_ff・補正の倍率 residual_scale。立つ → しゃがむ（1.0 s、胴体 35° 前傾、逆動力学のトルク）→ 0.2 s 止まる → 押し出し（hop.py の時間最適な押し出し、重心 3 cm、85 ms）→ 空中（伸びている脚を 20 ms で止め、頂点までに膝 80° に縮め、着地の 25 ms 前に膝 60°・つま先 20° 下げ）→ 着地（60 ms でつま先を戻す）→ 0.9 s で立ち姿勢へ（逆動力学のトルク）→ 0.8 s 静止。最初と最後の行は立ち姿勢・速度 0・トルク 0（歩行の方策との受け渡し）。
- 下位（`mdp.SkillReferenceJointPositionAction`）：物理の 1 ステップ（2.5 ms）ごとに表を線形補間して、目標角 q_ref + 0.25 × residual_scale × 行動、目標速度 dq_ref、トルク tau_ff をドライバの PD（MIT）に渡す。押し出しの間（とその 50 ms 前）は residual_scale 0.3。モータのモデル（`qdd_motor.py`）は 3 つの目標を同じ遅れ（0〜10 ms）で遅らせる（実機では 1 つの CAN フレーム）。
- 関門（`qdd_skill._validate_table`）：形式・関節の順序・有限・両端が立ち姿勢で静止・|tau_ff| ≤ 0.8 × ピーク・residual_scale 0.1〜1・離陸と着地の時刻が接地の予定と 0.04 s 以内。関節の参照（追従の報酬・速さなどの検査）は表の q になる。
- 方策は 100 Hz（物理 2.5 ms × 4）。行動の意味が変わったので歩行の方策からは始めず、最後の層を 0.01 倍にしてゼロから（行動 0 ＝ 表だけ）。行動のばらつきの初期値 0.5。
- 報酬の変更：転倒の罰 -50（× 10 ms ＝ 1 回 -0.5）、補正の大きさ |a|² に -0.05、補正の倍率を最初の 300 反復で 0.5 → 1。RSI は 70%（その 70% は押し出しの直前のしゃがみ 0.5 s の中から、跳ぶ場面を多く学ぶ）、押し出し・空中の途中からは始めない。γ 0.995（50 Hz の 0.99 と同じ時間の長さ）、2000 反復。
- policy_io：`skill.reference` に表、`action.target` に規則。Rust コントローラが同じ規則で 500 Hz で再生する（ロボットのリポジトリ `controller/`）。
- `qdd_biped.xml` を作り直した（6.607 kg、足 139 g）。1 回目の手書きのキーフレームの hop は `tests/fixtures/hop_keyframes.json`（関門の試験用）。
